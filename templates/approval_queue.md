# approval_queue — 承認キュー

> **外向き操作（送信・公開・正本の書き換え）は、ここに積まれる。実行されない。**
> エージェントは外向き操作にぶつかると、実行する代わりに1件書いて次の仕事へ移る。
> 人間は1日に数回ここを開けて、承認・修正・却下を捌く。

**書式のキモは「迷い」欄。** 承認する人間が全文を精読しなくても、*どこを見れば出荷判定できるか* をエージェントに申告させる。これでキュー捌きは1件あたり数十秒になる。この欄が無いと、人間が全成果物を精読するハメになり、ループの速度メリットが承認で全部溶ける。

**却下・修正の理由は捨てない。** 捌いたあと、却下/修正の理由を `decisions.md` に1件足す。週次でそれを蒸留して検証器を1本増やす（→ `docs/design.md`「却下の蒸留ループ」）。

**キューに載せる/載せないは2値でなく3値にする。** 人手の確認を伴う業務システム（請求書の自動仕訳など）では、**確信度で「自動確定／要確認／不可」に振り分ける**のが定石だ。同じ形をこのキューにも使う——エージェントが自信を持って処理でき、かつ戻せるものは自動確定。曖昧なものだけがキューに載る。不可（そもそも情報が足りない）は差し戻して調べ直す。**閾値を設定値として持てば、承認者が自分で無人化率を締めたり緩めたりできる**（安全度のつまみが承認者の手にある、という状態そのものが効く）。

**キューは滞留する。滞留したときの既定動作を先に決めておく。** 承認待ちが積むこと自体は避けられないので、載せる時点で6つの既定値を持たせる: **SLA（何日で捌く想定か）／督促の間隔／督促の回数／エスカレ先／再提出の期限／諦めたときの挙動**（そのまま流すのか・落とすのか・締切超過分だけ除いて先に進むのか）。決めていないと、1件の未処理が下流を全部止める。キューの健全性は「到着 N 件／処理 M 件／滞留 K 件」の3点セットで見る（→ [`../docs/judgment-distillation.md`](../docs/judgment-distillation.md)）。

エントリの型:

```markdown
## Q-YYYY-MM-DD-NN
- 種別: 送信 / 公開 / 正本更新 のいずれか（＋補足: 例「チャット返信の下書き」）
- 宛先: 誰に届くか（people.md の表示名で）
- 内容: 何をするか。要旨を1〜2行で
- 根拠: 元メッセージ（リンク）/ 参照した資料（リンク）/ 決定 ID
- 取り消し可能性: 不可 / 一部可（編集可）/ 可
- エージェントの迷い: どこが不確かか。どの解釈を採ったか
- [ ] 承認  / [ ] 修正して承認  / [ ] 却下（理由:            ）
```
