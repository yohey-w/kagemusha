# meeting-copilot — 判定層（§1.8）

`decision_backend` を `rules` 以外にするとき、`decisions.yaml` の問いや閾値を触るとき、`replay_eval.py` で採点するとき、費用を見積もるときに読む。外へ何が出るかの線は SKILL.md 本文の「判定層の要点」が要約している。

## 1.8 判定層（Decision Layer）— 発話ごとに「決めた問い」へ確率つきで答える

**第1層（番人）はキーワード照合だけで動く。** 速くて落ちないのが取り柄だが、
書いた言葉と同じ言葉が出たときしか当たらない。会議で人は毎回違う言い方をするので、
実走ではここが軒並み外れた（段の切替4回は全部たまたま一致した無関係な語、
口にした約束は1件も記録に残らなかった）。

判定層は、その判定だけを**差し替えられる口**にする層。

```
発話 ─▶ state（直近K発話だけ）＋ questions（問いの束）
     ─▶ DecisionEngine.evaluate() ─▶ 問いごとの答えと確率
     ─▶ （確信度ゲート）─▶ カード
```

| 実装 | 何をするか | 外へ出るか |
|---|---|---|
| `JevBackend` | 設定した宛先へ REST で1往復。問いは全部1回に積む | 出る |
| `LLMBackend` | 同じ問いの束を、小型 LLM に JSON で答えさせる（OpenAI 互換） | 出る |
| `RulesBackend` | いまのキーワード判定（`step_detect` / `lookup_assist`）を同じ問いの形に包んだもの | **出ない** |
| `ChainEngine` | 上を順に試して、答えた実装で止まる。**どれが答えたかを記録に残す** | 途中で止まれば出ない |

**退避の順序は `fallback_chain`**（既定
`[jev, "llm:anthropic/claude-haiku-4.5", rules]`）。前から順に試し、答えた実装で
止まります。**最後は必ず `rules`**——外へ出ない実装で終わらないと、全部落ちたときに
答えが1つも出ません（書き忘れても足します）。使わない段は外してよく、
`[jev, rules]` なら LLM を挟みません。`base_url` が空の段は鎖から自動で外れます。

段は `llm:<モデル>` と書けて、**同じ名前の段を何段でも**並べられます
（1つ目の小型 LLM が落ちたら2つ目へ）。段ごとにタイムアウトを変えるなら辞書で:

```yaml
fallback_chain:
  - jev
  - {llm: anthropic/claude-haiku-4.5, timeout_sec: 2.0}
  - "llm:openai/gpt-5.6-luna-fast"     # 1つ目が落ちたらこちら
  - rules
```

`decisions.jsonl` の `backend` 欄に、**実際に答えた段がモデル名まで**残ります
（`jev` / `llm:anthropic/claude-haiku-4.5(fallback)` / `rules(fallback)`）。
どのモデルが答えたのか分からないと、並べて測った意味が無くなるためです。
ここを見ないと「判定器で測った」つもりの数字が実はルールの数字、が起きます
——実測で 2,077発話のうち 1,754 が退避でした。

### 小型 LLM を中段に置くとき

判定器が使えないとき（枠のレート制限・障害・契約前）の受け皿です。同じ問いの束を
言葉に直して送り、`{問いid: {"value":…, "confidence":…}}` の JSON で答えさせます。
**判定器ではない**ので、本物と違うところが2つあります。

- **確率分布が返りません。** 確信度1つから近似して埋め、答えに `approx: true` を
  立てます。校正の表を読むときは、この印の付いた行を**混ぜないこと**
- **崩れた JSON が返りえます。** 厳格に読み、選択肢に無い値は**丸めずに捨て**、
  1問も読めなければ答えを捏造せず次の退避先へ渡します

`--backend llm` で LLM 単独の成績を測れます（鎖を LLM から始める）。
`--llm-model <モデル>` を足すと、そのモデル1つ＋ルールの鎖になります
（測っているモデルが途中で入れ替わらないよう、後ろの `llm` 段は外れます）。
Jev と並べて的中率を見てから、どちらを本線にするか決めてください。

🔴 **この道具は宛先を内蔵しない。** 送り先・鍵の環境変数名・モデル名は設定ファイル側。
設定に宛先が無ければ Jev は起動しません（既定は `rules`＝外へ1バイトも出ない）。

### 1.8.1 問いの束 — `decisions.yaml`

会議フォルダ直下に置きます。置かなくても動きます（同梱の
`config/decisions.example.yaml` に落ちる）。問いの束は案件に依らず、
**候補だけ**が会議フォルダから来るためです。

| 問い | 型 | 候補の出どころ | 誰の発話で聞くか |
|---|---|---|---|
| `q1_step` 段 | choice | `agenda_steps.json` の段＋`none` | 両方 |
| `q2_phase` 局面 | score | opening / body / closing / ended | 両方 |
| `q3_kind` 発話の種類 | choice | 8択（事実・質問・決定・約束…） | 両方 |
| `q4_lookup` 探し物 | noul | — | **進行役だけ** |
| `q5_quick_fact` 探し物はどの行か | choice | `quick_facts.md` の見出し＋`none` | 両方 |
| `q8_commitment` 約束 | noul | — | **進行役だけ** |

`q1_step` には `criteria_detail: true` を足せます（既定 false）。候補の説明に、
段の見出しだけでなく進行表の**「取る答え」**を添えます——見出しは4〜8文字しかなく、
判定材料として薄いことがあるためです（実測: 検収の段を「該当なし」と答える誤りが
48件中11件）。1問が長くなる＝入力トークンが増えるので、再生で効き目を確かめてから。

問いを足しても往復は増えません（1回の呼び出しの中で並列に答えます）。
進行役だけの問いは、相手の発話のときは**組み立てません**。候補が0件の問いは
丸ごと外します（「該当なし」しか選べない問いは料金だけ掛かります）。

型ごとの注意:

- **閾値は型ごとに別で調整する。** 同じ問いでも choice と noul では返る数字の
  大きさが違います。片方で決めた値をもう片方へ流用しないこと。
- **noul に確信度はありません**（返るのは「はい」の確率だけ）。校正を見るときの
  確信度は `max(p, 1-p)` と決めてあります。
- **`instructions` は書いたとおりにしか読まれません。** 含みを持たせず、
  「誰の」「いつの」発話について聞いているかを毎回書くこと。
- **日本語は精度が落ちます。** 閾値は保守的に始めて、再生の的中率を見てから緩めます。

### 1.8.2 送る物 — 直近K発話だけ・人名は伏せる

```yaml
window:
  utterances: 8        # 直近8発話。逐語の蓄積は送らない
  max_chars: 1200      # 1発話が異様に長いときの保険
privacy:
  roster: roster.txt   # 会議フォルダの名簿（1行1名・任意）
  host_alias: 〈進行役〉
  guest_alias: 〈相手〉
```

窓を切るのは料金のためではありません。判定器は **state が伸びるほど精度が落ちます**
（判定に関係のない材料が答えを引っ張る）。

人名の置換は **送る物の全体**に掛かります——発話だけでなく、段の見出しや即答表の
見出しにも相手の名前が入りうるからです。名簿に姓名を空白区切りで書くと、
**姓だけ・名だけでも**伏せます（会議では姓だけで呼ばれる方が普通なため）。

`roster.txt` を作り忘れても、`meeting.json` の `counterpart` / `host_label` に
書いてある呼び方は**自動で名簿に入ります**（敬称は落とします）。ただしこれは
書き忘れの保険であって、出席者を数え上げたことにはなりません。

🔴 **だから名簿の関門は、保険の件数では開きません。** 見るのは
`roster.txt` というファイルが**在ること**と、**中身が1件以上あること**だけです。

| 経路 | 名簿が無い／空のとき |
|---|---|
| `replay_eval.py --backend jev`(や `llm`) | **止まります**。作るか `--allow-no-roster` で明示的に押し切るか |
| 会議中（`copilot.py`） | **外へ送る段（`jev` / `llm`）を組み立てません**。ルールだけで動き、起動ログに🔴で理由が出ます |

判定は同じ関数（`decision_engine.roster_gate`）で、**両方の経路が同じ規則**です。
片方だけ緩いと緩い方から漏れます（会議中の経路だけが名簿の中身で分岐して実名が出た穴を、
独立レビューで見つけて塞いだ経緯は §5.9（[`design-notes.md`](design-notes.md)） と [`docs/provenance.md`](../../../../docs/provenance.md)）。

🔴 **これは匿名化の保証ではありません。** 書き漏らした名前は素通りしますし、
文脈から相手が分かることもあります。何を外へ出すかは、`decisions.jsonl` に残った
**送った物の現物**を見て判断してください（`--dry-run` なら送る前に見られます）。

### 1.8.3 鍵の置き場所

🔴 **鍵はファイルに書きません。** 設定に書くのは**環境変数の名前**だけです。

```yaml
jev:
  base_url: <送り先>          # 例: ゲートウェイ経由 / 直契約の API
  path: /v1/systemone
  model: <モデル名>
  key_env: AI_GATEWAY_API_KEY  # ← 鍵そのものではなく、鍵が入る変数の名前
  timeout_sec: 2.0             # 2秒。再試行はしない（遅れて出るカードは邪魔）
```

小型 LLM の宛先は別の枠（`llm:`）に書きます。ゲートウェイ経由なら**同じ鍵**が
使えるので、`key_env` は同じ名前で構いません。

走らせる側で `export AI_GATEWAY_API_KEY=...` します。鍵を会議フォルダに置かないのは
合言葉と同じ理由です（§1.5（[`SKILL.md`](../SKILL.md)））。鍵が空のときは判定が例外になり、Rules へ退避します
——会議は止まりません。

### 1.8.4 採点 — `replay_eval.py`

会議は1日1回しか来ません。閾値を当日の勘で決めると、外したことに気づくのは次の会議の
最中になります。**終わった会議の逐語を流し直して**、発話ごとに判定層を叩きます。

```bash
# ルール判定だけで最後まで通す（鍵は要らない・外へ出ない）
python3 scripts/replay_eval.py \
  --transcript <逐語.jsonl> --meeting <会議フォルダ> --backend rules

# 何を外へ送るのかだけ見る（1件も送らない）
python3 scripts/replay_eval.py \
  --transcript <逐語.jsonl> --meeting <会議フォルダ> --backend jev --dry-run

# 外の判定器で採点する
export AI_GATEWAY_API_KEY=...
python3 scripts/replay_eval.py \
  --transcript <逐語.jsonl> --meeting <会議フォルダ> \
  --backend jev --labels labels.csv
```

出るもの: 問いごとの**的中率**・**対象外**（正解は付いているが、その発話では
聞いていない問いの件数。q4/q8 は進行役の発話にしか聞かないので、相手の発話に
付いた正解は分母に入れません）・noul の**再現率**（閾値 0.5 と 0.8）・
**確信度ごとの的中率**（校正の簡易確認。数字どおりに当たっていれば右肩上がり）・
**p50/p95 の遅延**・**総トークンと概算費用**・どの実装が答えたかの内訳。

**レート制限のある枠で回すとき**（無料枠は実測でおよそ10回/分。2,077発話を流したら
320しか通らず、残りは 429 でルールへ退避した）:

| 旗 | 何をするか |
|---|---|
| `--ids <file>` | 判定する発話を絞る（`utterance_id` を1行1つ）。**窓の文脈は逐語全体から取る**ので、間引いても直前の話は欠けません |
| `--pace <秒>` | 呼び出しの間隔。既定 0 |
| `--retry-on-429` | 混雑(429/503)のときだけ、退避せず `--pace` ぶん待って**1回だけ**撃ち直す。既定 off。**会議中は使わない**——待つぶんカードが遅れるので、会議では待たずにルールへ退避するのが正しい |

正解を付けた発話だけを拾うのがいちばん効きます（`--ids` に正解表の `utterance_id` を
渡す）。判定の回数は減りますが、採点に使える数は変わりません。

正解表 `labels.csv` は3列。**発話の番号は逐語ファイルの1始まりの行番号**です。

```csv
utterance_id,q,gold
142,q1_step,s3
142,q8_commitment,yes
```

`gold` に書くのは鍵（`s3` `none` `yes` `no` `closing`）。鍵と見出しの対応は
`--dry-run` が先頭に出します。

### 1.8.5 費用の見方

単価は設定に書きます。**0 のままなら費用は計算しません**——この道具は他所の値段を
内蔵しないためです（値段は変わりますし、経路によっても違います）。

```yaml
pricing:
  input_per_mtok: 0.042   # 入力100万トークンあたり。自分が契約した単価を書く
  output_per_mtok: 0.0
  currency: USD
```

`decisions.jsonl` の各行に `usage` が入っているので、会議1回ぶんを足せば実績が出ます。
再生の最後に概算が出ますが、**これは記録した usage からの算術であって請求書ではありません**。

### 1.8.6 会議中に何が出るか

| 設定（`meeting.json`） | 既定 | 意味 |
|---|---|---|
| `decision_backend` | `"rules"` | 判定層を何で回すか。`"jev"` にすると外へ出る |
| `show_decision_cards` | `false` | 判定の答えをカンペに出すか。既定は**記録だけ** |

どちらも既定のままなら、判定層は組み立てすらしません。`decision_backend` を
`jev` にすると記録が溜まりはじめ、`show_decision_cards` を `true` にして初めて
画面が変わります。**閾値は先に `replay_eval.py` で実測してから**画面に出す、の順です。

**判定は本線の外で、発話ごとに走ります。** 1発話ごとに鎖のタイムアウト合計だけ
本線が待つ作りにすると、発話が4秒に1本来る会議では二度と追いつきません。かといって
班を1本に絞ると、鎖が遅い日は「走行中につき見送り」が大半になり、**カードが
まったく出ない会議**になります。だから班は **3本まで重ねて走らせ**、それでも
溢れたら**いちばん古い未完了を諦めます**（新しい発話の方が価値がある。古い判定が
今ごろ返ってきても、会話は先へ行っている）。

- 諦めた判定は、返ってきても**画面には出さず記録だけ**残します
  （`decisions.jsonl` に `"abandoned": true`。採点では混ぜないこと）
- 「諦める」は結果を捨てて枠を空けることで、通信を止めることではありません
  （走っているスレッドは外から止められない）。タイムアウトで自然に終わります
- 起動時に「1発話あたり最大◯秒」を読み上げ、**4秒 × 班の本数**を超える鎖のときだけ
  警告します。同梱の鎖は 2.0（判定器）＋1.5（小型 LLM）＝**3.5秒**に収めてあります
- 会議中は混雑しても**撃ち直しません**（待つぶんカードが遅れるだけ）

| 問い | 出るもの | 既定の境目 |
|---|---|---|
| Q8 約束 | **3行カード**（【対象】いまの段 or 相手の直前の発話／【状況】進行役がいま約束した「逐語40字」／【言うこと】確定なら「はい」と一声 → 台帳へ記帳）。宛先は「進行役へ」。同じ発話で1枚だけ | `0.8` |
| Q4 探し物 | 既存の即答表アシストを起動（**合図の語と OR**。言い回しは毎回違うので両方で拾う）。カードの形は従来どおり | `0.5` |
| Q1 段 | カンペ上部に小さく「推定の段: ④…」。**段は動かしません**（切替は従来どおりキーワードの規則。外したときに台本が飛ぶため） | `0.8` |
| Q3 種類 | 画面には出ません。`small_talk` と判定したら**直後の催促を見送る**だけ | `0.8` |
| Q2 局面 | `ended` が3発話続いたら終話の**予鈴**。**予鈴は停止ではありません**——畳むには従来どおり無音が続くことが必要です | `0.8` / `streak: 3` |

境目は `decisions.yaml` の各問いの `thresholds:` で変えられます（`act:` が確信度、
Q2 だけ `streak:` も見ます）。**確信が足りないものは何もしません**——外れたカードは、
無いカードより悪いからです。

判定層が例外を投げても番人は生き続けます（ログだけ残して次の発話へ）。
前提監視は**従来どおり同期で動きます**——Q3 で絞ると、判定層が落ちた日に
前提監視まで消えるためです（実測で退避率85%の日がありました）。
